## 〇、结论摘要（30 秒版）

1. **现状**：v0.7 特效全部程序化（glow/glow_ring/粒子/伤害数字），资产侧 15 张 fx 序列帧只用了 14 张、`fx_hit_spark.png` 零引用。**四个结构性问题**：每次特效 new 一个 `CanvasItemMaterial`（`fx.gd:297-300`）打断批处理；`hitstop` 全局压 `Engine.time_scale=0.05`（`fx.gd:249`，`projectile.gd:119` 每次非暴击命中都触发）；**零池化**，每次命中 new 3 个节点（glow Sprite + 8 粒 CPUParticles2D + Label）；`glow_aura` 生命周期完全依赖调用者 `queue_free`（`fx.gd:88-98`），是潜在泄漏点。
2. **超武合成演出**：在 `player.gd:1102-1105` 现有四件套（glow 300 + ring 170 + shake 14 + hitstop 0.12）基础上升级为 **0.9s 三幕分镜**，新增开销仅 **+6 DrawCall / +5 节点 / +66 粒子**，60 敌满弹幕最坏场景峰值 DrawCall ≈ 232 ≤ 250 ✅。
3. **弹幕可读性**（新威胁的生死线）：敌方弹幕一律「冷色高饱和核心（亮度 ≥0.85）+ 白描边 2px + ADD 光晕 ≥1.5× 弹体」，玩家弹一律暖金无描边——玩家 0.2 秒内即可区分「我要躲的」和「我在打的」。
4. **对象池**：6 类特效池（总 188 个节点上限）+ **共享单例 ADD 材质**（`fx.gd:297` 必改）+ 同帧节流（每类 ≤6 次）。同屏 CPUParticles2D 系统数 ≤24、粒子实例总量上限 **650**（红线 800 触发降级）。
5. **hitstop 双通道约定**：打击通道（A1 修复后：冷却窗口 0.15s 内不重复触发、只保留 0.03-0.05s 微顿）与演出通道（合成/ Boss 阶段转换独占，可 0.12s 全局顿帧）分离——这条约定是 v0.8「爽点 ①」能落地的前提。

## 一、特效语言与配色（总语法）

全游戏特效用**三层语言**，玩家不需要学习即可读懂：

| 层 | 语义 | 配色域 | 混合 | 亮度纪律 |
| --- | --- | --- | --- | --- |
| **玩家/友方** | 我在输出 | 暖色：金 `#FFD75E`、橙 `#FF9A3C`、青白 `#9FE8FF` | ADD | 无描边，靠 ADD 光晕提亮 |
| **敌方威胁** | 我要躲 | 冷色高饱和：酸绿 `#8CFF4A`、警戒红 `#FF4A4A`、深渊紫 `#B44AFF` | ADD + 白描边 2px | 核心亮度 ≥0.85（背景地砖 ≤0.35，对比 ≥2.4:1） |
| **稀有/奖励** | 这是好东西 | 档位色：普通=蓝 `#4FC3F7`、稀有=紫 `#C77DFF`、传说=金 `#FFD700` | ADD | 爆发半径按档位 200/260/340px 递增 |

- **z_index 只允许 6 档**：2（地面纹样）/ 3（拖尾、光环）/ 4（弹体）/ 5（技能体）/ 6（爆发、冲击环）/ 10（伤害数字）。z 档碎片化会打断 2D 批处理，这条是 DrawCall 预算的隐形守门员。
- **纹理只用两张程序化渐变图**：`_glow_texture`（128px，`fx.gd:12-28`）与 `_glow_ring_texture`（256px，`fx.gd:31-47`）已缓存为 static var——这是现成的图集化基础，池化后全特效只提交 2 张纹理。

## 三、超武合成演出方案（v0.8 爽点 ① 的视觉承载体）

### 3.1 设计意图

设计终稿 §1.1：v0.7 的合成演出**从未被玩家见过**（9.8% 以下可达率）；v0.8 修复后 ≥90% 的局至少一次——这是玩家第一次"见证奇迹"的时刻，必须一次看懂三件事：**「我变强了（金色）」「全场停了一下（顿帧）」「这是这一局的高光（震屏+粒子）」**。基座复用 `player.gd:1102-1105` 现有四件套，不引入新系统。

### 3.2 分镜时序表（精确到毫秒，T0 = 三选一确认超武、升级浮层关闭瞬间）

| 时刻 | 幕 | 内容 | 实现载体 | 与动画/音频对齐点 |
| --- | --- | --- | --- | --- |

**工程注意（必须提给主程序）**：`Engine.time_scale=0.05` 期间所有 tween 会同步变慢（`fx.gd:250` 的 timer 用了 `ignore_time_scale=true`，但视觉 tween 没有）——**演出通道的全部 tween 必须 `tween.set_ignore_time_scale(true)`**，否则 0.9s 演出会被拖成 3s+。这是 v0.7 隐性 bug，随 A1 一并修。

### 3.3 开销核算（最坏场景：同屏 60 敌 + 满弹幕 + 合成瞬间）

**基准帧 DrawCall 构成（合成瞬间，按共享材质修复后估算）**：

| 项 | 估算 DC | 说明 |
| --- | --- | --- |
| 地面（A5 烘焙后） | 1–3 | 单张 ImageTexture |
| 玩家 + 常驻光环 + 诅咒光环 | 3 | |
| 敌人 60 只（4–6 种贴图） | 10–20 | 同贴图相邻可批；按 6 类型保守计 |
| 尸体 ≤3 + 宝石 ≤20 | ≤23 | |
| 玩家弹 40 颗（弹体+共享拖尾纹理） | 45–80 | 拖尾改用 glow 纹理后可批 |
| **敌方弹幕 40 颗** | 40–80 | 弹体 + 光晕（共享纹理/材质） |
| HUD（`hud.gd` 纯代码 UI） | 30–45 | |
| **基准小计** | **≈ 175–230** | |

**合成演出增量**：

| 项 | 增量 | 存续 |
| --- | --- | --- |
| CanvasModulate | +1 | 0.9s |
| 光柱 Sprite + glow | +2 | 0.85s / 0.35s |
| glow_ring ×3 | +3 | 各 0.6s（交错） |
| CPUParticles2D ×3（30+16+20） | +3（节点）| 最长 0.9s |
| 金尘/碎片/环火粒子 | +66 粒 | ≤0.9s |
| 常驻金光环 | +1 | 本局常驻（计入光环预算） |
| **合计** | **+6 DrawCall / +10 节点 / +66 粒子** | |

**结论**：最坏基准 230 + 6 = **236 ≤ 250** ✅；节点峰值增量 10（900 预算内，且 0.9s 后归还池）；粒子瞬时 +66，在 §五总量预算内。**演出期间不触发任何 hit_spark/damage_number（顿帧内敌人不掉血），不存在叠加尖峰。** 测量方式：`Performance.RENDER_TOTAL_DRAW_CALLS_IN_FRAME` 每 60 帧采样，合成瞬间抓 p99。

## 五、性能预算与对象池

### 5.1 CPUParticles2D vs GPUParticles2D（Web 取舍论证）

**结论：坚持 CPUParticles2D，不上 GPUParticles2D。** 论证：

1. 渲染器是 GL Compatibility（`project.godot:63-64`），GPUParticles2D 在 WebGL2 可用，但低端机（iPhone 8 / 骁龙 660）GPU 驱动对 per-system 顶点缓冲分配/销毁的开销不可控——我们每秒创建/销毁几十个粒子系统（池化后仍高频复用 restart），GPU 缓冲抖动风险高。
2. CPUParticles2D 的粒子更新在引擎 C++ 内完成（非 GDScript），单系统 ≤30 粒时每帧成本 <0.02ms，桌面实测单帧总逻辑 4ms 预算内可容纳 24 个系统。
3. Web 单线程（`export_presets.cfg:24`），两者都在主线程，GPUParticles 无异步优势。
4. **预留回退开关**：若真机实测（Chrome DevTools Performance）CPU 粒子耗时 p95 >1.5ms，再评估批量迁移 GPUParticles2D——v0.8 不做。
